## 구현 완료

### 완료: 추천 이유 고도화와 추천 히스토리 저장

완료 내용:

- 홈 개인화 추천 이유를 관심 분야, 읽은 책 키워드, 저장한 책 키워드, 읽은 책 카테고리, 저장한 책 카테고리 기준으로 구체화했다.
- 홈 개인화 추천이 선택되면 `recommendations`에 `CONTENT_BASED` 유형으로 저장한다.
- `recommendations`의 `(user_id, book_id, recommendation_type)` unique key를 기준으로 중복 저장을 방지한다.
- 기존 추천이 다시 생성되면 `reason`, `score`만 갱신하고 `generated_at`은 최초 추천 시각으로 유지한다.
- 마이페이지 추천 히스토리에서 저장된 reason, source, score, generatedAt을 표시한다.
- 홈 화면에서 API가 정상적으로 빈 배열이나 `todayRecommendation: null`을 반환할 때 mock 데이터로 덮어쓰지 않도록 정리했다.
- 홈의 급상승, 인기, 카테고리 랭킹 빈 상태 문구를 추가했다.

검증:

- backend: `cd backend; .\gradlew.bat test` 성공
- frontend: `cd frontend; npm run build` 성공

### 완료: 서비스 고유 기능 강화

완료 내용:

- 책 상세 API에 `filterReport`, `recommendationEvidence`, `readingGuide` 응답 필드를 추가했다.
- `filterReport`는 교양 필터 상태, 노출 이유, 대표 카테고리, 주요 키워드를 제공한다.
- `recommendationEvidence`는 대표 분야, 공통 키워드, 교양 필터 근거를 최대 3개 카드로 제공한다.
- `readingGuide`는 이 책이 맞을 수 있는 사용자와 비슷한 책 비교 메모를 제공한다.
- 데이터 출처가 없는 난이도, 독서 분위기, 제외 키워드 부재는 단정하지 않도록 제외했다.
- 책 상세 화면에 교양 필터 리포트, 추천 근거, 읽을 책 결정 보조 섹션을 추가했다.
- 데이터가 없는 경우 새 섹션을 숨기는 fallback을 적용했다.
- 홈의 `교양 독서 기준 TOP 리스트`에서 카테고리별 반복 `더보기`를 제거하고, 섹션 제목 근처 단일 이동 링크로 정리했다.

검증:

- backend: `cd backend; .\gradlew.bat test` 성공
- frontend: `cd frontend; npm run build` 성공

## 앞으로 구현할 내용

### 1순위: 검색 기반 책 추가

현재 온보딩의 읽은 책 입력은 backend가 제공하는 선택지 목록 기반이다. 사용자가 실제로 읽은 책이나 저장할 책을 빠르게 찾기 어렵기 때문에 내부 DB 검색 기반 추가 기능을 먼저 구현한다.

상세 계획:

- `docs/plan/2026-04-29/priority-1-search-based-book-addition-plan.md`

목표:

- 사용자가 온보딩과 마이페이지에서 책을 직접 검색해 읽은 책 또는 저장한 책으로 추가할 수 있게 한다.
- 외부 도서 API 연동 없이 현재 DB의 책 데이터를 우선 활용한다.
- 검색 결과가 없거나 적을 때도 화면이 깨지지 않고 다음 행동을 안내한다.

1차 구현 범위:

- 내부 DB 기반 책 검색 API
- 온보딩 읽은 책 검색 입력
- 마이페이지 읽은 책 추가 검색 입력
- 마이페이지 저장한 책 추가 검색 입력
- 검색 결과 선택 시 기존 `user_book_interactions` 흐름으로 `READ` 또는 `SAVE` 저장
- 검색 결과 없음, 짧은 검색어, 서버 오류 상태 문구

backend 상세 계획:

1. `GET /api/books/search?query=...&limit=...` API를 추가한다.
2. `query`는 제목, 저자, 키워드, 카테고리 중 현재 repository/JPA 또는 JDBC로 안전하게 처리 가능한 범위부터 검색한다.
3. 기본 limit은 10, 최대 limit은 20으로 제한한다.
4. 빈 query 또는 너무 짧은 query는 400 또는 빈 배열 중 기존 API 스타일에 맞춰 결정한다.
5. 응답은 기존 `BookSummaryResponse`를 우선 재사용한다.
6. `generalEligible=true` 책만 검색 결과에 노출한다.
7. 검색 API 테스트를 추가한다.

frontend 상세 계획:

1. 온보딩의 읽은 책 선택 영역에 검색 입력을 추가한다.
2. 마이페이지의 읽은 책/저장한 책 영역에 추가 검색 UI를 배치한다.
3. 입력 debounce는 간단한 지연 처리로 시작하거나, 명시적 검색 버튼 방식으로 시작한다.
4. 검색 결과는 기존 `BookCard`보다 더 조밀한 선택 목록으로 표시한다.
5. 이미 선택한 책은 중복 추가되지 않도록 비활성화하거나 선택 상태를 표시한다.
6. `READ`, `SAVE` 저장은 기존 상호작용 API를 우선 재사용한다.

검증 계획:

- backend 변경 후 `cd backend; .\gradlew.bat test`
- frontend 변경 후 `cd frontend; npm run build`
- 수동 확인: 짧은 검색어, 결과 없음, 중복 선택, 로그인 만료, 모바일 입력 영역

주의 사항:

- 외부 도서 API 연동은 네트워크, API key, 데이터 저장 정책이 필요하므로 별도 범위로 분리한다.
- 검색 정확도보다 안정적인 내부 DB 검색과 기존 상호작용 저장 흐름 연결을 우선한다.

### 2순위: 독서 목적 저장과 추천 반영

계획 문서에는 독서 목적 선택이 포함되어 있지만 현재 온보딩 저장 요청에는 독서 목적 전용 저장 구조가 없다. 추천 이유를 더 설득력 있게 만들기 위해 독서 목적을 명시적으로 저장하고 추천 근거에 반영한다.

상세 계획:

- `docs/plan/2026-04-29/priority-2-reading-purpose-plan.md`

목표:

- 사용자가 책을 찾는 목적을 온보딩에서 선택할 수 있게 한다.
- 독서 목적을 추천 후보 점수와 추천 이유 문구에 반영한다.
- 마이페이지에서 독서 목적을 확인하고 수정할 수 있게 한다.

1차 구현 범위:

- 독서 목적 후보 정의
- 온보딩 독서 목적 선택 UI
- 마이페이지 독서 목적 조회/수정 UI
- 독서 목적 저장 API와 조회 API
- 홈 개인화 추천 이유에 독서 목적 반영

독서 목적 후보:

- 지식 확장
- 자기계발
- 경제/투자 이해
- 가벼운 독서
- 트렌드 파악

backend 상세 계획:

1. 독서 목적 저장 위치를 결정한다.
2. DB schema 변경이 필요하면 구현 전 별도 승인을 받는다.
3. 온보딩 저장 요청에 독서 목적 ID 또는 코드 목록을 포함한다.
4. 마이페이지 응답에 현재 독서 목적을 포함한다.
5. 추천 점수 계산에서 독서 목적과 카테고리/키워드의 매핑을 반영한다.
6. 추천 이유는 `recommendations.reason`의 `VARCHAR(255)` 제약 안에서 짧게 생성한다.
7. 저장, 조회, 추천 반영 테스트를 추가한다.

frontend 상세 계획:

1. 온보딩 단계에 독서 목적 선택 영역을 추가한다.
2. 선택 개수는 1~3개로 제한한다.
3. 마이페이지 취향 관리 영역에서 독서 목적을 수정할 수 있게 한다.
4. 홈 오늘의 추천 이유에서 독서 목적 반영 문구가 자연스럽게 보이는지 확인한다.
5. 선택하지 않은 사용자는 기존 추천 흐름이 그대로 동작하게 한다.

검증 계획:

- backend 변경 후 `cd backend; .\gradlew.bat test`
- frontend 변경 후 `cd frontend; npm run build`
- 수동 확인: 신규 온보딩, 기존 사용자, 목적 미선택, 목적 변경 후 홈 추천 이유

주의 사항:

- DB schema 변경 가능성이 높으므로 구현 전 승인 대상이다.
- 독서 목적과 추천 후보 매핑은 초기에 규칙 기반으로 시작하고, 데이터가 쌓인 뒤 조정한다.

### 3순위: 데이터 기반 추천 확장

현재 추천은 콘텐츠 기반 규칙과 제한된 사용자 행동 데이터를 활용한다. 충분한 행동 로그가 쌓이면 랭킹, 유사 도서, 유사 사용자 추천을 데이터 기반으로 확장한다.

상세 계획:

- `docs/plan/2026-04-29/priority-3-data-driven-recommendation-plan.md`

목표:

- 조회, 저장, 읽음, 관심 없음 데이터를 추천 품질 개선에 활용한다.
- 단순 카테고리/키워드 기반을 넘어 사용자 행동을 반영한 추천 후보를 만든다.
- README의 트렌드 피드와 개인 맞춤 추천을 장기적으로 강화한다.

1차 구현 범위:

- 추천 품질 개선을 위한 이벤트와 지표 정의
- 랭킹 점수 산식 정리
- 유사 도서 점수 산식 개선
- 사용자 행동 기반 후보 제외/가중치 강화
- 추천 결과 검증 지표 문서화

backend 상세 계획:

1. 현재 저장되는 사용자 행동 이벤트를 정리한다.
2. 추가로 필요한 이벤트가 있으면 schema/API 변경 필요 여부를 분리한다.
3. 랭킹 점수에 조회수, 클릭률, 저장 수, 리뷰 수, 최근 상승률을 어떻게 반영할지 산식을 정한다.
4. 유사 도서 추천에서 카테고리 일치, 공통 키워드, 저장/읽음 기반 가중치를 분리한다.
5. `DISMISS`와 `READ` 책은 개인 추천 후보에서 제외하는 기존 정책을 유지한다.
6. 후보 생성, 점수 계산, fallback 정책 테스트를 추가한다.

frontend 상세 계획:

1. 홈 추천 카드와 상세 추천 근거가 새 점수 근거와 모순되지 않도록 문구를 정리한다.
2. 트렌드 피드에서 급상승 근거를 짧게 표시할지 검토한다.
3. 추천 근거가 없는 경우 기존 fallback 문구를 유지한다.
4. 사용자가 저장/읽음/관심 없음 처리 후 추천 화면이 갱신되는 UX를 점검한다.

검증 계획:

- backend 변경 후 `cd backend; .\gradlew.bat test`
- frontend 변경 후 `cd frontend; npm run build`
- 수동 확인: 신규 사용자, 행동 데이터가 많은 사용자, 후보 부족, 관심 없음 처리 후 추천 제외

주의 사항:

- 초기에는 데이터가 적어 추천 품질이 낮을 수 있다.
- 유사 사용자 추천은 개인정보와 데이터 희소성 문제가 있으므로 MVP 이후 별도 계획으로 분리한다.
- 리뷰 또는 키워드 기반 감정 분석은 별도 AI/ML 파이프라인 계획이 필요하다.

## 남은 리스크

- 추천 이유는 아직 `VARCHAR(255)` 제약 안에서 짧게 유지해야 한다.
- 추천 히스토리는 같은 책이 다시 추천되면 reason과 score가 갱신되므로, 과거 reason의 변경 이력까지 보존하지는 않는다.
- 독서 목적은 DB schema 변경 가능성이 높아 구현 전 별도 승인이 필요하다.
- 외부 도서 API 연동은 검색 기반 책 추가의 1차 범위에서 제외한다.
- 데이터 기반 추천 확장은 충분한 사용자 행동 데이터가 쌓이기 전에는 품질 검증이 어렵다.
