## 구현 완료

### 완료: 추천 이유 고도화와 추천 히스토리 저장

상세 계획 파일:

- 구현 완료에 따라 삭제함

완료 내용:

- 홈 개인화 추천 이유를 관심 분야, 읽은 책 키워드, 저장한 책 키워드, 읽은 책 카테고리, 저장한 책 카테고리 기준으로 구체화했다.
- 홈 개인화 추천이 선택되면 `recommendations`에 `CONTENT_BASED` 유형으로 저장한다.
- `recommendations`의 `(user_id, book_id, recommendation_type)` unique key를 기준으로 중복 저장을 방지한다.
- 기존 추천이 다시 생성되면 `reason`, `score`만 갱신하고 `generated_at`은 최초 추천 시각으로 유지한다.
- 마이페이지 추천 히스토리에서 저장된 reason, source, score, generatedAt을 표시한다.
- 홈 화면에서 API가 정상적으로 빈 배열이나 `todayRecommendation: null`을 반환할 때 mock 데이터로 덮어쓰지 않도록 정리했다.
- 홈의 급상승, 인기, 카테고리 랭킹 빈 상태 문구를 추가했다.

검증:

- backend: `cd backend; .\gradlew.bat test` 성공
- frontend: `cd frontend; npm run build` 성공

## 앞으로 구현할 내용

### 1순위: 서비스 고유 기능 강화

계획 문서의 차별화 기능은 아직 별도 화면이나 컴포넌트로 닫히지 않았다.

구현할 내용:

- 교양 필터 리포트
  - 교양서로 분류된 이유
  - 제외 키워드가 없는 이유
  - 주요 카테고리와 키워드
  - 수험서, 문제집, 전공서 성격이 낮은 근거
- 추천 근거 카드
  - 관심 분야와의 연결
  - 읽은 책과의 연결
  - 저장한 책과의 연결
  - 최근 독서 트렌드와의 연결
- 읽을 책 결정 보조
  - 이 책을 읽기 좋은 사용자
  - 읽기 난이도
  - 예상 독서 분위기
  - 비슷한 책과의 차이

주의 사항:

- 새 데이터 필드가 필요한 항목은 먼저 현재 DB에 표현 가능한지 확인한다.
- 난이도, 분위기, 제외 근거는 데이터 출처가 불명확하면 정적 문구로 시작하지 않는다.

상세 계획:

- `docs/plan/2026-04-29/priority-1-service-unique-features-plan.md`

### 2순위: 검색 기반 책 추가

현재 온보딩의 읽은 책 입력은 backend가 제공하는 선택지 목록 기반이다.

구현할 내용:

- 읽은 책 검색 입력
- 저장한 책 검색 입력
- 검색 결과에서 읽은 책 또는 저장한 책으로 추가
- 검색 결과가 없을 때의 안내

backend 필요 API 후보:

- `GET /api/books/search?query=...`

주의 사항:

- 외부 도서 API 연동은 네트워크, API key, 데이터 저장 정책이 필요하므로 별도 범위로 분리한다.
- 우선 내부 DB 검색으로 시작한다.

### 3순위: 독서 목적 저장과 추천 반영

계획 문서에는 독서 목적 선택이 포함되어 있지만 현재 온보딩 저장 요청에는 없다.

구현할 내용:

- 독서 목적 선택 UI
- 독서 목적 저장 위치 결정
- 독서 목적 기반 추천 이유와 후보 조정

주의 사항:

- 현재 확인한 코드 기준으로 독서 목적 전용 schema는 없다.
- DB schema 변경 가능성이 높으므로 구현 전 별도 승인이 필요하다.

### 4순위: 데이터 기반 추천 확장

사용자 행동 데이터가 충분히 쌓인 뒤 진행할 항목이다.

구현할 내용:

- 행동 로그 기반 랭킹 개선
- 유사 도서 추천 개선
- 유사 사용자 추천
- 리뷰 또는 키워드 기반 감정 분석

주의 사항:

- 초기에는 데이터가 적어 추천 품질이 낮을 수 있다.
- MVP 이후 지표 수집 기준을 먼저 정해야 한다.

## 권장 구현 순서

1. 교양 필터 리포트와 추천 근거 카드 설계
2. 검색 기반 책 추가 계획 분리
3. 독서 목적 저장 계획 분리
4. 데이터 기반 추천 확장은 MVP 이후 지표 수집 기준부터 정리

## 검증 계획

문서만 변경할 때:

- 별도 빌드 검증은 필요하지 않다.
- 문서 링크와 변경 내용을 확인한다.

후속 frontend 변경 시:

```powershell
cd frontend
npm run build
```

후속 backend 변경 시:

```powershell
cd backend
.\gradlew.bat test
```

frontend/backend를 함께 변경할 때는 두 검증 명령을 모두 실행한다.

## 남은 리스크

- 추천 이유는 아직 `VARCHAR(255)` 제약 안에서 짧게 유지해야 한다.
- 추천 히스토리는 같은 책이 다시 추천되면 reason과 score가 갱신되므로, 과거 reason의 변경 이력까지 보존하지는 않는다.
- 독서 목적과 난이도/분위기 정보는 현재 데이터 모델에서 바로 표현하기 어려울 수 있다.
