# 게이미피케이션 확장 계획

## 기준

- 작성일: 2026-04-29
- 기준 문서:
  - `README.md`
  - `docs/plan/2026-04-29/mvp-gap-and-expansion-check-plan.md`
- 목적: ChaekList의 1차 MVP 이후 확장 방향으로 SNS보다 먼저 적용할 수 있는 개인 성장형 게이미피케이션 방안을 정리한다.
- 범위: planner 역할 문서화만 수행한다. frontend/backend 코드, API, DB schema 변경은 포함하지 않는다.

## 방향성 판단

ChaekList의 확장 방향은 초기에는 SNS보다 게이미피케이션이 더 적합하다.

이유:

- ChaekList의 핵심 문제는 사용자가 읽을 책을 고르는 피로감을 줄이는 것이다.
- 현재 구현과 계획은 관심 분야, 읽은 책, 저장한 책, 추천 히스토리, 독서 목적 같은 개인 데이터 중심이다.
- 게이미피케이션은 이 개인 데이터를 자연스럽게 쌓게 만들고, 추천 품질을 높이는 입력으로도 쓸 수 있다.
- SNS는 게시글, 좋아요, 팔로우, 알림, 신고, moderation, 초기 빈 피드 문제가 함께 따라온다.
- 초기 사용자 수가 충분하지 않으면 SNS 피드는 비어 보일 가능성이 높다.

따라서 1차 확장은 "독서 SNS"보다 "내 취향과 독서 성장이 보이는 추천 앱" 방향이 안전하다.

## 목표

- 사용자가 독서 기록을 남길 동기를 만든다.
- 읽은 책, 저장한 책, 독서 목적, 카테고리 탐색 기록을 개인 성장으로 시각화한다.
- 단순 권수 경쟁이 아니라 교양 독서의 깊이와 다양성을 보여준다.
- 추천 시스템에 필요한 사용자 행동 데이터를 더 자연스럽게 축적한다.

## 원칙

- 경쟁보다 개인 성장에 초점을 둔다.
- 책 권수만 보상하지 않는다.
- 짧은 책을 많이 읽는 행동만 유리하게 만들지 않는다.
- 미완독, 탐색, 저장, 관심 없음 같은 행동도 취향 학습의 일부로 본다.
- 사용자가 독서에 압박을 느끼지 않도록 부드러운 문구를 쓴다.
- 랭킹형 경쟁, 리그, 공개 순위는 1차에서 제외한다.

## 현재 데이터 기반으로 가능한 것

현재 또는 1차 MVP 이후 확보 가능한 데이터:

- 관심 분야
- 읽은 책 `READ`
- 저장한 책 `SAVE`
- 저장 취소 `UNSAVE`
- 관심 없음 `DISMISS`
- 추천 히스토리
- 책 카테고리
- 책 키워드
- 독서 목적
- 랭킹/급상승 지표

이 데이터로 바로 만들 수 있는 성장 요소:

- 읽은 책 수
- 저장한 책 중 읽음 전환 수
- 카테고리별 읽은 책 분포
- 키워드별 탐색 분포
- 독서 목적별 진행도
- 추천 받은 책 중 저장/읽음 전환
- 관심 없음 처리로 취향이 정리된 정도

## 1차 게이미피케이션 범위

### 개인 성장 요약

마이페이지에 개인 독서 성장 요약을 추가한다.

표시 후보:

- 이번 달 읽은 책
- 저장한 책 중 읽은 책으로 바뀐 수
- 가장 많이 읽은 분야
- 최근 넓어진 분야
- 추천을 통해 발견한 책 수

주의:

- "레벨이 낮다"처럼 사용자를 평가하는 문구는 피한다.
- 권수보다 변화와 탐색을 중심으로 표현한다.

### 독서 성장 레벨

레벨은 경쟁 점수가 아니라 개인 진행 상태로 사용한다.

레벨 후보:

- Level 1: 탐색 시작
- Level 2: 취향 발견
- Level 3: 분야 확장
- Level 4: 독서 루틴 형성
- Level 5: 교양 탐험가

점수 입력 후보:

- 읽은 책 1권: +10
- 저장한 책을 읽음으로 전환: +12
- 새 카테고리 첫 읽음: +15
- 독서 목적과 맞는 책 읽음: +10
- 추천 받은 책을 저장: +5
- 추천 받은 책을 읽음: +15

주의:

- 점수는 내부 계산용으로 두고, UI에서는 부드러운 진행률로 보여준다.
- 추후 변경 가능성이 크므로 초기에 과도한 레벨 이름이나 보상 체계를 고정하지 않는다.

### 배지

배지는 사용자의 독서 성향을 설명하는 용도로 시작한다.

배지 후보:

- 인문 탐색가: 인문 분야 읽은 책 3권
- 경제 입문자: 경제/투자 키워드 책 3권
- 넓게 읽는 사람: 서로 다른 카테고리 3개 이상 읽음
- 저장에서 완독까지: 저장한 책 3권을 읽음으로 전환
- 트렌드 캐처: 급상승 도서 또는 트렌드 키워드 책 3권 저장/읽음
- 취향 정리 중: 관심 없음 처리 5회로 추천 후보 정리

주의:

- 배지는 사용자를 압박하지 않는 표현을 쓴다.
- "완독"이라는 단어는 실제 완독 여부를 확인할 데이터가 없으면 `읽은 책` 표현을 우선한다.

### 목적별 진행도

독서 목적 기능이 구현된 뒤 추가한다.

예시:

- 지식 확장: 인문/사회/역사/AI 키워드 책 읽음
- 자기계발: 습관/집중/루틴 키워드 책 읽음
- 경제/투자 이해: 경제/투자/시장 키워드 책 읽음
- 가벼운 독서: 에세이/소설/일상/관계 책 읽음
- 트렌드 파악: AI/도파민/트렌드/기술/투자 키워드 책 읽음

주의:

- 목적별 진행도는 독서 목적 저장 기능 이후 구현한다.
- 목적과 책의 매핑은 규칙 기반으로 시작하되, 과장된 문구는 피한다.

### 주간/월간 리포트

초기에는 마이페이지 안의 요약 카드로 시작한다.

리포트 후보:

- 이번 달 가장 많이 읽은 분야
- 이번 달 새로 탐색한 키워드
- 저장만 해둔 책 수
- 추천에서 읽음으로 이어진 책 수
- 다음에 읽으면 좋은 분야

주의:

- "부족하다", "밀렸다" 같은 압박 문구를 쓰지 않는다.
- 독서 기록이 적은 사용자는 빈 상태 안내와 추천 행동을 제공한다.

## 1차 제외 범위

- 사용자 간 게시글 작성
- 좋아요, 댓글, 팔로우
- 공개 리더보드
- 유저 간 독서 경쟁
- 친구 초대 기반 미션
- 랭킹 보상
- 유료 포인트/재화
- 푸시 알림 기반 streak 압박
- 복잡한 아바타/캐릭터 성장 시스템

## backend 구현 계획

대상 후보:

- `backend/src/main/java/com/example/chaeklist/domain/mypage/service/MyPageService.java`
- `backend/src/main/java/com/example/chaeklist/domain/mypage/dto/MyPageResponse.java`
- `backend/src/main/java/com/example/chaeklist/domain/book/service/BookService.java`
- `backend/src/test/java/com/example/chaeklist/MyPageControllerTest.java`

작업 순서:

1. 현재 `user_book_interactions`와 `recommendations`로 계산 가능한 성장 지표를 확정한다.
2. 마이페이지 응답에 `readingGrowth` 후보 필드를 설계한다.
3. 읽은 책 수, 저장 후 읽음 전환 수, 카테고리 다양성, 추천 전환 수를 계산한다.
4. 성장 레벨 계산 규칙을 service 내부 메서드로 분리한다.
5. 배지 조건 계산을 작은 메서드로 분리한다.
6. 데이터가 부족한 사용자에게는 빈 상태용 응답을 내려준다.
7. 테스트에서 신규 사용자, 읽은 책 있는 사용자, 저장 후 읽은 사용자, 다양한 카테고리 사용자 케이스를 검증한다.

응답 구조 후보:

```json
{
  "readingGrowth": {
    "level": 2,
    "levelName": "취향 발견",
    "progressPercent": 45,
    "summary": "경제 분야와 투자 키워드를 중심으로 취향이 쌓이고 있습니다.",
    "monthlyReadCount": 3,
    "savedToReadCount": 1,
    "categoryDiversityCount": 2,
    "badges": [
      {
        "code": "ECONOMY_STARTER",
        "label": "경제 입문자",
        "description": "경제/투자 분야 책을 꾸준히 읽고 있습니다."
      }
    ]
  }
}
```

주의:

- 별도 테이블 없이 계산 가능한 값부터 시작한다.
- 배지 획득 이력을 영구 저장하려면 schema 변경이 필요하므로 2차로 분리한다.
- 성장 점수는 사용자가 직접 보는 절대 점수보다 진행률과 설명으로 노출한다.

## frontend 구현 계획

대상 후보:

- `frontend/src/pages/MyPage.jsx`
- `frontend/src/pages/HomePage.jsx`
- `frontend/src/pages/OnboardingPage.jsx`

마이페이지:

1. 사용자 요약 근처에 독서 성장 카드 추가
2. 레벨명, 진행률, 이번 달 읽은 책, 분야 다양성 표시
3. 배지는 2~4개 정도만 표시
4. 기록이 부족하면 읽은 책 추가 또는 저장한 책 읽음 처리로 연결

홈:

1. 로그인 사용자에게 오늘의 추천 아래 짧은 성장 힌트 표시 검토
2. 추천 이유와 성장 힌트가 중복되면 마이페이지로만 제한

온보딩:

1. 온보딩 완료 후 첫 성장 상태를 간단히 안내할지 검토
2. 초기에는 온보딩 화면에 게이미피케이션을 과하게 넣지 않는다.

UI 기준:

- 조용하고 정보 밀도 있는 카드로 표시한다.
- 대형 축하 화면보다 마이페이지의 지속적인 기록 영역으로 둔다.
- 진행률 바는 사용하되 경쟁적인 랭킹 UI는 피한다.
- 배지는 작고 설명 가능한 라벨로 둔다.

## 확장 확인 필요

### 데이터

- `READ`가 실제 완독 의미인지, 사용자가 직접 표시한 읽음 의미인지 명확히 해야 한다.
- 월간 기준을 `created_at` 기준으로 볼지 별도 완료 날짜가 필요한지 확인해야 한다.
- 저장 후 읽음 전환은 `SAVE` 이후 `READ` 이벤트 순서로 볼지 결정해야 한다.
- 추천을 통해 읽음으로 이어졌는지 판단하려면 추천 히스토리와 interaction 시간 비교가 필요하다.

### schema

- 1차는 계산형 응답으로 시작한다.
- 배지 획득 날짜, 성장 기록 스냅샷, 주간 리포트 저장이 필요하면 별도 schema가 필요하다.
- schema 변경 전에는 `user_book_interactions`와 `recommendations`만 사용한다.

### UX

- 독서량이 적은 사용자가 위축되지 않도록 표현을 조심한다.
- 숫자 목표보다 "분야 확장", "취향 발견", "추천 정확도 개선" 중심으로 표현한다.
- 연속 기록이나 streak는 푸시/압박 UX로 이어질 수 있으므로 1차에서 제외한다.

## SNS 확장과의 관계

게이미피케이션을 먼저 구현하면 SNS 확장의 재료가 생긴다.

나중에 연결 가능한 SNS 요소:

- 내 독서 성장 카드 공유
- 이번 달 읽은 분야 공유
- 배지 공개 여부
- 추천받아 읽은 책 공유
- 공개 프로필에서 성장 요약 표시

주의:

- 게시글/좋아요/댓글은 moderation과 초기 피드 문제를 동반하므로 별도 후속 계획으로 분리한다.
- SNS는 개인 성장 데이터가 충분히 쌓인 뒤 선택적으로 공개하는 방향이 자연스럽다.

- 배지 조건 충족/미충족

## 권장 구현 순서

1. 마이페이지 계산형 독서 성장 카드
2. 기본 배지 3~5개
3. 독서 목적 구현 후 목적별 진행도
4. 월간 리포트 카드
5. 성장 카드 공유 또는 공개 프로필 연동

## 남은 리스크

- 데이터가 적은 초기 사용자에게는 성장 카드가 빈약하게 보일 수 있다.
- 권수 중심 보상은 독서 품질보다 양을 유도할 수 있다.
- 배지 조건이 너무 많으면 관리 비용이 커진다.
- 성장 점수와 추천 점수가 섞이면 사용자가 오해할 수 있으므로 UI에서 분리해야 한다.
