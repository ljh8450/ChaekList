## README 기준 1차 MVP 축

README의 MVP와 핵심 해결책을 기준으로 1차 MVP는 다음 축으로 본다.

- 교양 전용 랭킹
- 교양 필터링
- 기본 개인 맞춤 추천
- 트렌드/급상승 피드
- 비로그인 홈 인기 책 노출
- 책 상세 탐색
- 온보딩과 마이페이지를 통한 취향/읽은 책 관리

## 현재 구현된 것으로 보는 항목

### 교양 전용 랭킹과 홈 피드

- 홈에서 현재 인기 책, 급상승 책, 카테고리별 랭킹을 표시한다.
- 랭킹 API는 최신 snapshot 기준 전체/카테고리/급상승 목록을 반환한다.
- 홈의 빈 데이터 fallback 문구가 정리되어 있다.
- `교양 독서 기준 TOP 리스트`의 카테고리 탭 이동은 섹션 제목 근처 단일 `더보기` 링크로 정리되어 있다.

확장 확인 필요:

- snapshot 데이터가 실제 운영 데이터로 주기적으로 갱신되는지 확인해야 한다.
- `ranking_score` 산식이 수집/배치 단계에서 계산되는지, API에서 단순 조회만 하는지 경계를 확인해야 한다.
- 급상승 정렬이 `recent_growth_rate`만 볼지, 동률 시 저장 수나 ranking score를 보조 정렬로 볼지 결정해야 한다.

### 기본 개인 맞춤 추천

- 홈 개인화 추천은 관심 분야, 읽은 책, 저장한 책의 카테고리/키워드를 기반으로 점수를 계산한다.
- 추천 결과는 `recommendations`에 `CONTENT_BASED` 유형으로 저장된다.
- 마이페이지에서 추천 히스토리 reason, source, score, generatedAt을 확인할 수 있다.
- `READ`, `DISMISS` 책은 개인 추천 후보에서 제외된다.

확장 확인 필요:

- 추천 점수 가중치를 상수화하고 테스트 가능한 단위로 분리할 필요가 있다.
- `VIEW`, `CLICK` 이벤트를 추천 산식에 바로 반영할 만큼 충분히 수집되는지 확인해야 한다.
- 추천 reason이 실제 점수 요인과 항상 일치하는지 테스트로 고정해야 한다.
- `recommendations.reason`의 `VARCHAR(255)` 제약 안에서 근거 문구를 유지해야 한다.

### 책 상세의 서비스 고유 기능

- 책 상세 API에 `filterReport`, `recommendationEvidence`, `readingGuide`가 추가되어 있다.
- 상세 화면에서 교양 필터 리포트, 추천 근거, 읽을 책 결정 보조 섹션을 표시한다.
- 데이터 출처가 없는 난이도, 독서 분위기, 제외 키워드 부재는 단정하지 않는다.

확장 확인 필요:

- `filter_reason` 원본 품질이 낮을 때 화면 설득력이 떨어질 수 있다.
- `recommendationEvidence`가 개인 추천 근거처럼 오해되지 않도록 문구를 계속 점검해야 한다.
- 외부 API로 새 책을 저장할 경우 `filterReport`에 표시할 `filter_status`, `filter_reason`, 카테고리, 키워드 초기값 정책이 필요하다.

## 1차 MVP에서 빠진 핵심 항목

### 1. 검색 기반 책 추가

현재 상태:

- 온보딩은 `/api/me/onboarding-options`가 제공한 책 목록 안에서 읽은 책을 선택하는 구조다.
- 마이페이지는 읽은 책과 저장한 책을 조회하지만, 직접 검색해서 추가하는 UI는 없다.
- 내부 DB나 seed data에 없는 책은 검색할 수 없다.

MVP에서 빠진 점:

- 사용자가 실제로 읽은 책을 자유롭게 검색해 추가할 수 없다.
- 사용자가 저장하고 싶은 책을 마이페이지에서 검색해 추가할 수 없다.
- 로컬 DB에 없는 책을 외부 도서 API로 찾는 흐름이 없다.

확장 확인 필요:

- 카카오 책 검색 API를 1차 MVP 범위에 포함할지 확정해야 한다.
- 이미 카카오 API를 사용 중이라면 책 검색 API도 같은 공급자로 확장하는 것이 자연스럽다.
- 내부 DB 검색만 먼저 할지, 내부 검색과 카카오 외부 검색을 같은 이슈에서 함께 구현할지 결정해야 한다.
- 외부 검색 결과를 언제 DB에 저장할지 결정해야 한다.
  - 검색 결과 표시 시 즉시 저장
  - 사용자가 선택할 때만 저장
- 권장안은 사용자가 선택한 책만 저장하는 방식이다.

구현 전 결정할 것:

- `GET /api/books/search?query=...&limit=...`가 내부 DB와 카카오 결과를 모두 반환할지
- 외부 검색 결과 선택 시 별도 import API를 둘지
- 기존 `/api/me/books/{bookId}/interactions`가 외부 결과 import까지 처리할지
- 카카오 API key 환경변수명
- ISBN13이 없는 결과 처리 방식
- 카카오 category를 ChaekList category로 매핑할지, 초기에는 `미분류` 또는 `PENDING`으로 둘지
- 신규 저장 책의 `is_general_eligible`, `filter_status`, `filter_reason` 초기값

권장 1차 흐름:

1. 내부 DB 검색을 먼저 수행한다.
2. 내부 결과가 없거나 부족하면 backend에서 카카오 책 검색 API를 호출한다.
3. 내부 결과와 외부 결과를 공통 검색 결과 DTO로 내려준다.
4. frontend는 같은 목록 UI로 표시한다.
5. 사용자가 선택하면 backend에서 ISBN13 기준 중복을 확인한다.
6. 기존 책이면 기존 book id를 사용한다.
7. 없는 책이면 `books`에 저장한다.
8. 이후 기존 interaction 흐름으로 `READ` 또는 `SAVE`를 저장한다.

### 2. 독서 목적 저장과 추천 반영

현재 상태:

- 온보딩 저장 요청은 `categoryIds`, `readBookIds`만 포함한다.
- 관심 분야는 `user_interest_categories`에 저장된다.
- 읽은 책과 저장한 책은 `user_book_interactions`에 저장된다.
- 독서 목적 전용 저장 구조는 없다.

MVP에서 빠진 점:

- 사용자가 책을 찾는 목적을 명시적으로 선택할 수 없다.
- 추천 reason에 “왜 지금 이 목적에 맞는지”를 반영할 수 없다.
- 마이페이지에서 독서 목적을 조회하거나 수정할 수 없다.

확장 확인 필요:

- 독서 목적을 1개만 받을지, 1~3개 다중 선택으로 받을지 결정해야 한다.
- DB schema 변경이 필요하므로 구현 전 승인이 필요하다.
- `user_reading_purposes` 별도 테이블을 둘지, user profile 성격의 단일 필드를 둘지 결정해야 한다.
- 목적 후보를 enum code로 관리할지, master table로 관리할지 결정해야 한다.
- 목적 기반 추천 점수는 관심 분야/읽은 책/저장한 책보다 낮은 보조 가중치로 둘지 확인해야 한다.

권장 1차 목적 후보:

- `KNOWLEDGE`: 지식 확장
- `SELF_IMPROVEMENT`: 자기계발
- `ECONOMY_INVESTING`: 경제/투자 이해
- `LIGHT_READING`: 가벼운 독서
- `TREND_TRACKING`: 트렌드 파악

권장 1차 흐름:

1. `/api/me/onboarding-options`에 독서 목적 후보를 포함한다.
2. 온보딩에서 1~3개를 선택한다.
3. `OnboardingRequest`에 `readingPurposeCodes`를 포함한다.
4. 저장 시 기존 사용자 목적을 교체 저장한다.
5. `/api/me/mypage`에서 현재 독서 목적을 내려준다.
6. 홈 개인화 추천 점수에 목적 기반 보조 점수를 반영한다.
7. reason은 실제 목적 근거가 있을 때만 짧게 반영한다.

### 3. 데이터 기반 추천 산식 정리

현재 상태:

- 개인 추천은 관심 분야, 읽은 책, 저장한 책의 카테고리/키워드 기반 규칙 점수로 동작한다.
- `READ`, `DISMISS` 후보 제외 정책은 있다.
- 랭킹 snapshot에는 조회 수, 클릭 수, 저장 수, 리뷰 수, 최근 상승률, ranking score가 있다.

MVP에서 빠진 점:

- 추천 점수 산식이 명확한 상수/메서드로 분리되어 있지 않다.
- 유사 도서 추천의 점수 기준이 제품 기준으로 문서화되어 있지 않다.
- 랭킹 지표가 개인 추천 fallback이나 유사 도서 추천에 어느 정도 반영될지 명확하지 않다.

확장 확인 필요:

- 개인 추천 가중치를 상수화할지 결정해야 한다.
- 랭킹 snapshot의 `ranking_score`를 개인 추천 보조 점수로 사용할지 확인해야 한다.
- 유사 도서 추천에서 같은 카테고리를 필수 조건으로 유지할지, 점수 요인으로 완화할지 확인해야 한다.
- `VIEW`, `CLICK` 이벤트가 실제 추천 입력으로 쓸 만큼 신뢰도 있게 쌓이는지 확인해야 한다.
- 데이터가 부족한 신규 사용자 fallback 정책을 테스트로 고정해야 한다.

권장 1차 정리:

- 관심 분야 카테고리 일치: +50
- 읽은 책 카테고리 일치: +25
- 저장한 책 카테고리 일치: +20
- 읽은 책 키워드 일치: 키워드당 +10
- 저장한 책 키워드 일치: 키워드당 +8
- 목적 기반 보조 점수는 독서 목적 구현 후 별도 추가
- `READ`, `DISMISS` 책은 후보 제외

## 1차 MVP 완료 판단 기준

- 온보딩에서 사용자가 실제 읽은 책을 검색해 추가할 수 있다.
- 마이페이지에서 읽은 책과 저장한 책을 검색해 추가할 수 있다.
- 로컬 DB에 없는 책도 카카오 책 검색으로 찾아 선택 저장할 수 있다.
- 사용자가 독서 목적을 선택하고 마이페이지에서 확인/수정할 수 있다.
- 홈 개인화 추천이 관심 분야, 읽은 책/저장한 책, 독서 목적 중 실제 데이터가 있는 근거만 사용한다.
- 추천 후보 제외, fallback, reason 저장 흐름이 테스트로 검증된다.

backend 변경 후:

```powershell
cd backend
.\gradlew.bat test
```

frontend 변경 후:

```powershell
cd frontend
npm run build
```

문서만 변경할 때:

- 별도 빌드 검증은 필요하지 않다.
- 문서 링크와 변경 내용을 확인한다.
