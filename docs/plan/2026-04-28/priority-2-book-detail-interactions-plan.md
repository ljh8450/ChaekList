# 다음 구현 계획: 책 상세 행동 추가

## 기준

- 작성일: 2026-04-28
- 상위 계획: `docs/plan/2026-04-28/follow-up-plan.md`
- 대상 항목: `1순위: 책 상세 행동 추가`
- 목적: 사용자가 책 상세에서 저장, 읽음, 관심 없음 행동을 직접 남기고 이후 마이페이지와 추천에 반영할 수 있게 한다.
- 범위: planner 역할 문서화만 수행한다. frontend/backend 코드, API, DB schema 변경은 포함하지 않는다.

## 현재 직후 구현 단위

다음 구현은 `책 상세 행동 추가`를 진행한다.

우선순위는 다음과 같다.

1. backend의 기존 interaction 모델, enum, repository, service 사용 방식을 확인한다.
2. DB schema 변경 없이 `SAVE`, `READ`, `UNSAVE`까지 먼저 연결 가능한지 판단한다.
3. `관심 없음`은 기존 허용 타입이 없으면 이번 구현에서 제외하거나 별도 승인 대상으로 분리한다.
4. 책 상세 화면에 사용자가 즉시 누를 수 있는 행동 버튼을 추가한다.
5. 행동 결과가 마이페이지의 저장한 책, 읽은 책 상태와 어긋나지 않게 확인한다.

## 구현 목표

1. 책 상세에서 저장하기를 수행할 수 있다.
2. 책 상세에서 읽었어요를 수행할 수 있다.
3. 이미 수행한 행동은 현재 상태로 표시한다.
4. 저장 취소가 필요하면 기존 `UNSAVE` 흐름을 우선 검토한다.
5. `관심 없음`은 schema 확인 뒤 안전한 방식으로만 포함한다.

## 1차 구현 범위

### 1. backend interaction 구조 확인

대상 위치:

- `backend/`

확인할 내용:

- interaction type enum 또는 문자열 허용 값
- `user_book_interactions` 저장 방식
- 기존 `READ`, `SAVE`, `UNSAVE` 사용 위치
- 책 상세 응답에 사용자별 행동 상태를 포함할 수 있는지
- 인증 사용자 식별 방식

결정 기준:

- DB schema 변경 없이 가능한 행동만 1차 구현에 포함한다.
- `DISMISS` 또는 `관심 없음` 저장 타입이 없으면 별도 승인 전에는 schema를 바꾸지 않는다.

### 2. 행동 저장 API 설계 또는 기존 API 재사용

대상 위치:

- `backend/`

후보 API:

- `POST /api/me/books/{bookId}/interactions`

요청 예:

```json
{ "type": "SAVE" }
```

```json
{ "type": "READ" }
```

응답 기준:

- 저장 후 현재 책에 대한 사용자 행동 상태를 반환한다.
- frontend가 별도 재조회 없이 버튼 상태를 갱신할 수 있게 한다.

주의 사항:

- 같은 행동을 반복 요청했을 때 중복 row가 생기지 않게 처리한다.
- 저장 취소는 기존 `UNSAVE`를 쓰는지, 별도 `DELETE`를 쓰는지 구현 전에 하나로 정한다.

### 3. 책 상세 UI 연결

대상 위치:

- `frontend/`

작업 내용:

- 책 상세 화면에 `저장하기` 버튼을 추가한다.
- 책 상세 화면에 `읽었어요` 버튼을 추가한다.
- 가능할 때만 `관심 없음` 버튼을 추가한다.
- API 요청 중에는 버튼 중복 클릭을 막는다.
- 실패 시 기존 에러 표시 패턴을 따른다.

권장 문구:

- 저장 전: `저장하기`
- 저장 후: `저장됨`
- 읽음 전: `읽었어요`
- 읽음 후: `읽은 책`
- 관심 없음: `관심 없음`

### 4. 상태 표시 범위

1차에서 확인할 상태:

- 책 상세에서 저장 여부 표시
- 책 상세에서 읽음 여부 표시
- 마이페이지 저장한 책 목록 반영
- 마이페이지 읽은 책 목록 반영

후속으로 미룰 수 있는 상태:

- 모든 책 카드에 행동 상태 뱃지 표시
- 추천 후보 가중치 반영
- 추천 히스토리 근거 문구 변경

## 제외 범위

이번 구현에서는 다음을 제외한다.

- DB schema 변경
- 외부 도서 API 연동
- 검색 기반 책 추가
- 추천 알고리즘 변경
- 추천 히스토리 저장 로직 변경
- 독서 목적 저장
- 관심 없음 타입을 위한 무승인 schema 확장

## 예상 변경 파일

구현 전 확인 후 확정한다.

가능성이 높은 frontend 파일:

- `frontend/src/pages/BookDetailPage.jsx`
- 책 상세 API 호출을 담당하는 기존 client/helper 파일
- 마이페이지 데이터 재조회 또는 상태 표시와 연결된 파일

가능성이 높은 backend 파일:

- 책 상세 controller/service
- 사용자 책 interaction controller/service
- interaction entity/repository/type 정의
- 책 상세 응답 DTO

## 구현 순서

1. backend에서 interaction 관련 타입과 저장 흐름을 확인한다.
2. 책 상세 응답에 사용자별 행동 상태가 이미 포함되는지 확인한다.
3. 없으면 최소 DTO 필드 추가가 필요한지 판단한다.
4. interaction 저장 API를 기존 패턴에 맞춰 설계한다.
5. DB schema 변경 없이 가능한 행동만 구현 범위로 확정한다.
6. 책 상세 UI에 행동 버튼과 요청 상태를 연결한다.
7. 마이페이지 저장한 책, 읽은 책 반영 여부를 확인한다.
8. frontend/backend 검증 명령을 실행한다.

## 검증 계획

frontend와 backend를 함께 변경할 가능성이 높으므로 구현 후 다음 명령을 모두 실행한다.

```powershell
cd frontend
npm run build
```

```powershell
cd backend
.\gradlew.bat test
```

수동 확인 항목:

- 책 상세에서 저장하기를 누르면 저장 상태가 표시된다.
- 저장한 책이 마이페이지 저장한 책 목록에 반영된다.
- 책 상세에서 읽었어요를 누르면 읽은 책 상태가 표시된다.
- 읽은 책이 마이페이지 읽은 책 목록에 반영된다.
- 같은 버튼을 여러 번 눌러도 중복 데이터가 생기지 않는다.
- 인증되지 않은 사용자는 기존 인증 흐름에 맞게 처리된다.

## 리스크와 후속 작업

- `관심 없음`은 기존 schema에 없을 가능성이 있어 별도 승인 없이는 제외될 수 있다.
- 책 상세 응답이 현재 사용자 상태를 담지 않으면 DTO와 service 변경 범위가 늘어난다.
- 저장 취소 UX는 `UNSAVE`와 `DELETE` 중 기존 코드에 맞는 방식을 확인한 뒤 확정해야 한다.
- 이 작업이 끝나면 다음 구현 단위는 `개인화 홈 추천 실제화`가 된다.
