## 앞으로 구현할 내용

### 1순위: 개인화 홈 추천 실제화

현재 `GET /api/me/home`은 `personalized = true`를 반환하지만 추천 책은 기본 랭킹 1위에 가깝다.

구현할 내용:

- 사용자의 관심 분야를 홈 추천 후보 가중치에 반영
- 읽은 책의 카테고리와 키워드를 추천 후보 가중치에 반영
- 저장한 책을 "나중에 읽을 후보" 신호로 반영
- 관심 없음으로 표시한 책의 카테고리/키워드 가중치 하향 또는 후보 제외
- 추천 이유를 사용자 행동 기반 문장으로 생성
- 홈 화면에서 실제 `GET /api/home`, `GET /api/me/home` 응답을 사용하도록 연결

초기 기준:

- 협업 필터링은 제외한다.
- 콘텐츠 기반 추천으로 시작한다.
- 추천 후보가 부족하면 기존 랭킹 기반 추천으로 fallback한다.

상세 계획:

- `docs/plan/2026-04-28/priority-3-personalized-home-recommendation-plan.md`

### 2순위: 추천 이유 고도화와 추천 히스토리 저장

현재 추천 이유는 카테고리 또는 필터 이유 중심의 일반 문장이다.

구현할 내용:

- 관심 분야 기반 추천 이유
- 읽은 책 기반 추천 이유
- 저장한 책 기반 추천 이유
- 공통 키워드 기반 추천 이유
- 생성된 추천 이유를 `recommendations`에 저장하는 기준 정리
- 마이페이지 추천 히스토리에 개인화 근거를 더 구체적으로 표시

좋은 추천 이유 형식:

- "읽은 책 `조용한 투자 습관`과 투자, 습관 키워드를 공유합니다."
- "관심 분야로 선택한 경제 분야에서 최근 저장이 늘어난 교양서입니다."

### 3순위: 서비스 고유 기능 강화

계획 문서의 차별화 기능은 아직 별도 화면이나 컴포넌트로 닫히지 않았다.

구현할 내용:

- 교양 필터 리포트
  - 교양서로 분류된 이유
  - 제외 키워드가 없는 이유
  - 주요 카테고리와 키워드
  - 수험서, 문제집, 전공서 성격이 낮은 근거
- 추천 근거 카드
  - 관심 분야와의 연결
  - 읽은 책과의 연결
  - 저장한 책과의 연결
  - 최근 독서 트렌드와의 연결
- 읽을 책 결정 보조
  - 이 책을 읽기 좋은 사용자
  - 읽기 난이도
  - 예상 독서 분위기
  - 비슷한 책과의 차이

주의 사항:

- 새 데이터 필드가 필요한 항목은 먼저 현재 DB에 표현 가능한지 확인한다.
- 난이도, 분위기, 제외 근거는 데이터 출처가 불명확하면 정적 문구로 시작하지 않는다.

### 4순위: 검색 기반 책 추가

현재 온보딩의 읽은 책 입력은 backend가 제공하는 선택지 목록 기반이다.

구현할 내용:

- 읽은 책 검색 입력
- 저장한 책 검색 입력
- 검색 결과에서 읽은 책 또는 저장한 책으로 추가
- 검색 결과가 없을 때의 안내

backend 필요 API 후보:

- `GET /api/books/search?query=...`

주의 사항:

- 외부 도서 API 연동은 네트워크, API key, 데이터 저장 정책이 필요하므로 별도 범위로 분리한다.
- 우선 내부 DB 검색으로 시작한다.

### 5순위: 독서 목적 저장과 추천 반영

계획 문서에는 독서 목적 선택이 포함되어 있지만 현재 온보딩 저장 요청에는 없다.

구현할 내용:

- 독서 목적 선택 UI
- 독서 목적 저장 위치 결정
- 독서 목적 기반 추천 이유와 후보 조정

주의 사항:

- 현재 확인한 코드 기준으로 독서 목적 전용 schema는 없다.
- DB schema 변경 가능성이 높으므로 구현 전 별도 승인이 필요하다.

### 6순위: 데이터 기반 추천 확장

사용자 행동 데이터가 충분히 쌓인 뒤 진행할 항목이다.

구현할 내용:

- 행동 로그 기반 랭킹 개선
- 유사 도서 추천 개선
- 유사 사용자 추천
- 리뷰 또는 키워드 기반 감정 분석

주의 사항:

- 초기에는 데이터가 적어 추천 품질이 낮을 수 있다.
- MVP 이후 지표 수집 기준을 먼저 정해야 한다.

## 권장 구현 순서

1. 개인화 홈 추천 후보 산정 로직 구현
2. 홈 화면 API 연동
3. 추천 이유 응답 구조 고도화
4. 추천 히스토리 저장 기준 정리
5. 교양 필터 리포트와 추천 근거 카드 설계
6. 검색 기반 책 추가와 독서 목적 저장은 별도 계획으로 분리

## 검증 계획

문서만 변경할 때:

- 별도 빌드 검증은 필요하지 않다.
- 문서 링크와 변경 내용을 확인한다.

후속 frontend 변경 시:

```powershell
cd frontend
npm run build
```

후속 backend 변경 시:

```powershell
cd backend
.\gradlew.bat test
```

frontend/backend를 함께 변경할 때는 두 검증 명령을 모두 실행한다.

## 남은 리스크

- `GET /api/me/home`은 개인화 플래그만 true인 상태라 사용자 기대와 실제 추천 품질 사이에 차이가 생길 수 있다.
- 개인화 후보 산정은 frontend, backend, 사용자 행동 데이터 해석을 함께 건드릴 수 있다.
- 추천 이유가 추상적이면 개인화 기능이 체감되지 않는다.
- `관심 없음` 행동이 실제 추천 하향 또는 제외로 이어지지 않으면 사용자가 행동 결과를 이해하기 어렵다.
- 독서 목적과 난이도/분위기 정보는 현재 데이터 모델에서 바로 표현하기 어려울 수 있다.
